# Healthed — გაშვების ინსტრუქცია

Healthed არის ქართული ინტერაქტიული ქუიზების პლატფორმა საზოგადოებრივი ჯანდაცვის, პრევენციისა და ჯანდაცვის მენეჯმენტის შესახებ. საიტი: https://healthed.club

ტექნიკური მოდელი: GitHub (კოდი), Cloudflare Pages (საიტი), Supabase (ანგარიშები, კითხვები, ქულები).

## რა არის მზად

ქუიზის დაწყებამდე მომხმარებელი ვალდებულია დარეგისტრირდეს ან შევიდეს ანგარიშში. დემო თამაში რეგისტრაციის გარეშე აღარ არის ხელმისაწვდომი.

ქართულენოვანი კატალოგი, მუქი/ნათელი თემა, რეგისტრაცია/შესვლა/გასვლა, 15/20/25/30-კითხვიანი ქუიზების სტრუქტურა, საერთო და თითო ქუიზის რეიტინგი, 15-კითხვიანი დღის ქუიზი, ტაიმერი, სერვერზე ქულების დათვლა, კითხვებისა და ქუიზების იმპორტი და დამტკიცება. განმარტებები და წყაროები ჩანს დასრულების შემდეგ.

ტაიმერი: 40 წამი თითო კითხვაზე, საერთო ქუიზზე გადანაწილებული (15 კითხვა = 10 წუთი). დროის ამოწურვისას უკვე მიღებული ქულები ინახება, დანარჩენი პასუხები ნულად ითვლება. საიტის დახურვა ტაიმერს არ აჩერებს.

რეიტინგი: პირველ ცდას ითვლის თითო ქუიზზე. თითო ქუიზზე სწორი პასუხების პროცენტი; საერთო რეიტინგში დასრულებული ქუიზების პროცენტების საშუალო. დღის ქუიზი ცალკე: დღეს/კვირაში/თვეში. განსხვავებული სირთულის ქუიზებისთვის საერთო რეიტინგი მიახლოებითი შედარებაა; თითო ქუიზის რეიტინგი უფრო პირდაპირია.

## მნიშვნელოვანი სტატუსი

მზად არის 30 წყაროიანი მონახაზი და ცალკე 15 დემოს კითხვა. 10,000-კითხვიანი დამტკიცებული ბაზა ჯერ არ არის შექმნილი. სისტემა არ შეიცავს ხელოვნურ 10,000 ვარიანტს. 30 მონახაზი საჭიროებს დამოუკიდებელ სამეცნიერო და ენობრივ შემოწმებას. 4 საწყისი ქუიზი საერთო, ფართო თემას ეკუთვნის: საზოგადოებრივი ჯანდაცვის საფუძვლები. ისინი ამ 30 კითხვის გადამკვეთ ნაკრებებს იყენებს; ცალკე, ვიწრო თემების კოლექციისთვის ახალი კითხვები საჭიროა.

დემო არ არის სასწავლო რეჟიმი ან რეალური ონლაინ რეიტინგი. ეს მხოლოდ ინტერფეისის სანახავი ქუიზია. მისი კითხვები არ უნდა მოხვდეს რეიტინგულ ბაზაში: პასუხები საჯარო დემოს ფაილშია.

კოდი შემოწმებულია PostgreSQL-ის ჩაშენებული PGlite გარემოთი და ბრაუზერის გარეშე ინტერფეისის ფუნქციების ტესტით. Supabase-ის რეალური რეგისტრაციისა და Cloudflare-ის შენი ანგარიშის შემოწმება საჭიროა დაკავშირების შემდეგ. ვიზუალური ბრაუზერული შემოწმება ამ გარემოში არ ჩატარებულა.

## 1. Supabase — პროექტის შექმნა

1. გახსენი https://supabase.com და შექმენი ანგარიში.
2. შექმენი ახალი პროექტი. ბაზის პაროლი შენთან შეინახე.
3. გახსენი SQL Editor → New query.
4. ჩასვი `supabase/schema.sql`-ის სრული ტექსტი და დააჭირე Run.
5. მეორე ახალ მოთხოვნაში ჩასვი `supabase/seed-drafts.sql` და დააჭირე Run.
6. პროექტის Connect/Settings ნაწილიდან აიღე Project URL და API Keys ნაწილიდან საჯარო publishable გასაღები ან legacy anon გასაღები.
7. არასოდეს გამოიყენო `service_role` ან `sb_secret_…` საიტის ფაილებში ან GitHub-ში.

SQL ფაილები განკუთვნილია ახალ, ცარიელ პროექტზე გასაშვებად. სხვა აპის არსებული ბაზისთვის წინასწარ მიგრაციის გეგმაა საჭირო.

## 2. მარტივი რეგისტრაცია

Authentication-ის Email პროვაიდერის პარამეტრებში ჩართე ელფოსტით შესვლა. თუ გინდა რეგისტრაციისთანავე თამაში, გამორთე Confirm email. გამოიყენება მეტსახელი, ელფოსტა და მინიმუმ 8-სიმბოლოიანი პაროლი; Supabase-ის საკუთარი პაროლის მოთხოვნაც შეიძლება მოქმედებდეს.

საჯაროდ მხოლოდ მეტსახელი ჩანს. უფასო გეგმას აქვს რესურსების ლიმიტები და დაბალი აქტივობის პროექტის შეჩერების შესაძლებლობა. რეგისტრაცია დადასტურების გარეშე ამარტივებს შესვლას, მაგრამ ანგარიშების რეალურ ელფოსტებს არ ამოწმებს. პაროლის აღდგენის გვერდი ამ ვერსიაში ჯერ არ არის დამატებული.

## 3. საიტის დაკავშირება

გახსენი `dist/config.js` და შეავსე მხოლოდ ეს ორი მნიშვნელობა:

```js
window.QUIZ_CONFIG = {
  url: 'https://შენი-პროექტის-იდენტიფიკატორი.supabase.co',
  key: 'შენი-საჯარო-publishable-ან-anon-გასაღები'
};
```

ბრაუზერის „დაკავშირება“ ღილაკით შეყვანა მხოლოდ იმ ბრაუზერისთვის მოქმედებს. ყველა მომხმარებლისთვის აუცილებელია config.js-ის შევსება და ახალი ვერსიის ატვირთვა.

## 4. GitHub

1. შექმენი ახალი private repository, მაგალითად `public-health-quiz`.
2. ZIP ამოარქივე. პროექტის ფაილები ატვირთე შენს საცავში (Add file → Upload files). საქაღალდეები შეინარჩუნე.
3. არ ატვირთო node_modules, .env ან რაიმე საიდუმლო გასაღები.
4. `.openai` საქაღალდე, თუ პაკეტშია, Cloudflare-ზე გადასატანად არ არის საჭირო. ჩამოსატვირთ პაკეტში ის გამორიცხულია.

## 5. Cloudflare Pages

1. გახსენი https://dash.cloudflare.com და შექმენი ანგარიში.
2. Workers & Pages → Create application → Pages → Connect to Git / Import existing Git repository (ღილაკის სახელი შეიძლება შეიცვალოს).
3. დააკავშირე GitHub-ის კონკრეტული საცავი.
4. Framework preset: None.
5. Build command: დატოვე ცარიელი.
6. Build output directory: `dist`.
7. Root directory: პროექტის ძირეული საქაღალდე.
8. Deploy. მიიღებ `…pages.dev` მისამართს.
9. Supabase → Authentication → URL Configuration-ში Site URL შეავსე ამ მისამართით.

ალტერნატივა: Pages-ის Direct Upload-ში ატვირთე მხოლოდ `dist`-ის შიგთავსი. თუმცა ავტომატური Git-განახლებებისთვის Git-ინტეგრაციით დაწყება ჯობს.

## 6. შენი ადმინისტრატორის უფლება

1. საიტზე შექმენი შენი ანგარიში.
2. Supabase → Authentication → Users-ში მოძებნე შენი მომხმარებელი და დააკოპირე მისი UUID.
3. SQL Editor-ში გაუშვი შემდეგი, UUID შენი რეალური მნიშვნელობით შეცვალე:

```sql
insert into public.editors(id)
values ('შენი-მომხმარებლის-UUID'::uuid)
on conflict do nothing;
```

4. საიტიდან გამოდი და ისევ შედი. ზედა მენიუში გამოჩნდება „მართვა“.
5. თითო კითხვაზე გახსენი წყარო და გადაამოწმე პასუხი, განმარტება და ქართული ფორმულირება. მონიშნე შემოწმების ველი და გამოაქვეყნე.
6. 15/20/25/30-კითხვიანი ქუიზები ცალკე გამოქვეყნდება მათი ყველა კითხვის დამტკიცების შემდეგ.

## 7. დღის ქუიზი

საქართველოს დროით ყოველი დღე იღებს 15 კითხვას, პირველ გაშვებაზე ქმნის საერთო უცვლელ ნაკრებს. ყველა მონაწილეს იგივე ნაკრები ეძლევა. შემდეგი დღის შერჩევაში იცვლება თარიღზე დამოკიდებული რიგი; დიდი ბაზა ამცირებს განმეორებას. მცირე ბაზა ყოველდღიურ უნიკალურობას ვერ უზრუნველყოფს.

საწყის კალენდარში მხოლოდ ორი გადამოწმებული დღეა: 7 აპრილი და 31 მაისი. სხვა მნიშვნელოვანი დღეები უნდა დაემატოს ოფიციალური წყაროს მიხედვით. ამ დღეებზე არჩეულ კონკრეტულ თემაში საჭიროა სულ მცირე 15 დამტკიცებული განსხვავებული კითხვა. თუ საკმარისი არ არის, თამაში აჩვენებს შეტყობინებას და შეუსაბამო თემით არ ანაცვლებს.

ახალი დღის მაგალითი (გამოიყენე მხოლოდ რეალური, წყაროთი დადასტურებული თარიღი):

```sql
insert into public.health_days(month_day,title,theme,source_url)
values ('MM-DD','დღის ქართული დასახელება','ბაზაში არსებული თემის ზუსტი სახელი','https://ზუსტი-ოფიციალური-წყარო');
```

## 8. ახალი კითხვები და ქუიზები

`data/questions.json` არის კითხვების ფორმატის ნიმუში. ატვირთვა: „მართვა“ → კითხვების JSON, მაქსიმუმ 500 ერთ ფაილში. კითხვები თავიდან მონახაზებია. სტატუსის ფაილიდან შეცვლა მათ ავტომატურად არ აქვეყნებს.

ახალი ქუიზების JSON არის მასივი ასეთი ობიექტებით:

```json
[{
  "id": "tobacco-policy-01",
  "title": "თამბაქოს კონტროლის თავსატეხები",
  "theme": "თამბაქოს კონტროლი",
  "question_count": 15,
  "question_ids": ["აქ ჩასვი 15 განსხვავებული კითხვის UUID"]
}]
```

საიტის მართვის გვერდზე ატვირთე ქუიზების კატალოგის JSON. თითო კითხვას უნდა ჰქონდეს ცალკე family_id; ერთი სცენარის ვარიანტები ერთ family_id-ში გააერთიანე. დამტკიცებული ახალი ვერსიისთვის ახალი ქუიზის ID გამოიყენე, რათა ძველი პირველი ცდის შედეგი ახალ ქუიზს არ შეერიოს.

## 9. 10,000 კითხვის შესრულების გეგმა

შექმენი თემების სარედაქციო რუკა; თითო თემისთვის შეკრიბე ოფიციალური სახელმძღვანელოები და კონკრეტული სტატიები; ყოველი მიგნებიდან დაწერე დამოუკიდებელი გადაწყვეტილების/ლოგიკის/ცოდნის კითხვა. გადაამოწმე სწორი პასუხის ცალსახაობა, განსხვავებული სცენარი, წყაროს შესაბამისობა და თარგმანი. გამოაქვეყნე შემოწმებული პარტიები. ითვლება დამტკიცებული განსხვავებული კითხვები და არა წინადადების გადაფორმულირებები. მთლიანი სტატიების კოპირება და არასანდო წყაროების ავტომატური გამოქვეყნება არ გამოიყენო.

## 10. გაშვების მიღების შემოწმება

ორი სხვადასხვა ანგარიშით შეამოწმე: რეგისტრაცია, ერთნაირი დღის ქუიზი, თითოეული ქუიზის სიგრძე, პირველი ცდის შენარჩუნება, ტაიმერის ამოწურვა, გასვლა/შესვლა, თითო ქუიზისა და დღის რეიტინგის გამიჯვნა. არადმინისტრატორს არ უნდა შეეძლოს კითხვების დამტკიცება. ბრაუზერის Network-ში სწორი პასუხები დასრულებამდე არ უნდა ჩანდეს. დემოს ფაილი გამონაკლისია და რეიტინგულ კითხვებს არ შეიცავს.

პროექტის ტესტები: `npm install`, შემდეგ `npm test`. PGlite-ის ტესტი Supabase-ის რეალურ ქსელს/ელფოსტას არ ამოწმებს.
